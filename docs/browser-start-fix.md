# 송파·올림픽 브라우저 시작 실패 분석 및 수정 (2026-10-09)

## 확인한 사실과 추정의 범위

첨부 화면은 송파 4개 시설과 올림픽이 브라우저 시작 단계에서 실패했음을 보여준다. 서버 자원 부족이라는 사용자 안내 문구는 오류 분류 결과이며, 실제 운영 로그나 PID·메모리 측정치는 확보하지 못했다. 따라서 운영 서버의 자원 고갈 원인은 아직 확정할 수 없다.

코드에서는 다음 문제가 확인됐다.

- 강동·하남은 HTTP 우선 조회지만 송파는 구현된 HTTP 경로가 기본 비활성 상태였다. 송파와 올림픽 조회마다 브라우저가 생성되고 종료됐다.
- 브라우저 실행의 Promise.race 타임아웃은 Playwright 실행을 취소하지 않았다. 타임아웃 후 늦게 생성된 context가 호출자에게 전달되지 않고 남을 수 있었다.
- provider 전체 타임아웃이 실제 작업 완료 전에 조회 잠금을 해제했다. 다음 조회가 진행 중인 브라우저와 같은 프로필을 사용할 수 있었다.
- 컨테이너에 고아 자식 프로세스를 회수할 init이 없었다. 반복 브라우저 생성·종료 환경에서 프로세스 누적을 방지하는 구성이 필요했다.
- 송파 세션 생성 후 페이지·route 초기화가 실패하면 context를 종료하지 않았다.

## 수정

송파 HTTP 기본값을 true로 변경했다. 실제 HTTP 요청에 30초 AbortSignal 제한시간을 주어 응답 본문 수신까지 취소할 수 있게 했다. 로그인 안내 문구가 정상 달력에 있어도 실제 로그인 폼과 구분한다. HTTP 실패 시 기존 LEGACY_HTTP_FALLBACK 설정에 따라 브라우저로 재시도한다.

브라우저 실행은 Playwright 자체 timeout을 사용해 실패한 실행을 정리한다. provider 잠금은 전체 조회 보고 타임아웃 이후에도 실제 작업과 정리가 끝날 때까지 유지한다. 송파 초기화 실패 시에도 context를 종료한다.

Dockerfile에 tini를 설치하고 entrypoint로 지정했다. Railway는 별도 startCommand가 Docker ENTRYPOINT를 덮어쓰므로 railway.json에도 `/usr/bin/tini -- node src/server.js`를 명시했다. 근거: [Railway 공식 시작 명령 문서](https://docs.railway.com/deployments/start-command).

## 검증 결과

- 전체 작업 폴더 테스트: 29개 파일, 283개 테스트 통과.
- 기존 미커밋 작업을 제외한 커밋 스냅샷 테스트: 26개 파일, 251개 테스트 통과.
- 송파 실제 계정의 HTTP 조회: 2026-10-10 기준 오륜 8개, 성내천 8개, 송파 5개, 오금 8개 회차 수신. 4개 시설 모두 성공, 약 0.6초. 해당 날짜 조회 시점에 예약가능 회차는 0개였다.
- 로컬 Chromium 실행 → 페이지 접근 → 종료 3회 성공.
- git diff --check 통과.
- Windows 로컬 실조회는 시스템 인증서를 사용하기 위해 `node --use-system-ca`로 실행했다. 인증서 검증은 유지했다.
- 올림픽 실계정 로그인은 실행하지 않았다. 운영 계정과의 중복 로그인 없이 브라우저 시작과 세션 관련 회귀 테스트로 검증했다.
- Docker 실행 도구가 없어 새 이미지 빌드와 Linux 프로세스 회수 동작은 로컬에서 검증하지 못했다.

## 운영 반영 시 확인

이 폴더의 Railway CLI에는 연결된 프로젝트가 없어 운영 설정 변경·배포·서버 로그 확인은 수행하지 않았다.

1. Railway Variables에 `SONGPA_HTTP_ENABLED=false`가 남아 있으면 true로 변경하거나 삭제한다. 명시적 환경변수는 코드와 Docker 기본값보다 우선한다.
2. 수정된 Dockerfile로 이미지를 다시 빌드해 재배포한다. 기존 컨테이너의 프로세스 누적을 해소하려면 새 컨테이너로 교체되어야 한다.
3. 서비스 시작 명령이 `/usr/bin/tini -- node src/server.js`인지 확인한다. 별도 명령으로 tini가 빠지지 않도록 한다.
4. 다음 조회 주기에 송파 4개 시설과 올림픽 성공 여부를 확인한다. 올림픽은 기존 KST 09:00~24:00 조회 시간과 단일 replica 조건을 유지한다.
5. 같은 오류가 지속되면 원문 launch 오류, cgroup pids.current/pids.max, memory.current/memory.max, 좀비 프로세스 수를 확인해 PID 제한과 메모리 부족을 구분한다.

기존 작업 폴더의 노원 연동 등 미커밋 변경은 보존했다.


## 후속: 13:50 송파 인증/파싱 오류와 올림픽 응답 지연

송파는 화면에 남은 과거 월 조건으로 실제 재현했다. 2026-10-09에 2026-09 달력을 요청하면 HTTP 200이지만 달력 대신 '잘못된 경로로 들어왔습니다. 자동로그아웃됩니다' 안내를 반환했다. 같은 세션에서 현재·다음 달 달력은 응답하므로 실제 세션 무효화 범위는 확정하지 않았다. 이 안내를 인증/달력 오류로 처리하는 것이 확인됐다. 따라서 모든 후속 실패가 실제 로그아웃 때문이라고 단정하지 않는다.

지난 날짜를 제거하고 2026-10-14, 17, 18 및 성내천 2026-11-27만 같은 HTTP 경로로 조회한 결과 오륜 16, 성내천 24, 송파 10, 오금 16 회차를 정상 수신했다. 휴장/대회 등 시간대 미표시 날짜는 회차를 만들어내지 않는다.

후속 수정:
- 자동·수동 감시 주기의 한국 날짜 기준 지난 조건을 제외한다. 저장된 조건은 삭제하지 않는다. KST 자정 경계와 실제 checker에 전달하는 날짜를 테스트했다.
- 송파 HTTP 시설별 실패를 오류 메타데이터에 기록하고 다른 시설의 결과를 보존한다. 달력 하나의 실패 때문에 모든 시설을 Chromium으로 재조회하지 않는다. 로그인 자체 실패에 대한 기존 fallback은 유지한다.
- 인증 응답과 파싱 실패를 별도 오류 유형으로 기록한다.
- 전체 작업 폴더 29개 파일 / 286개 테스트 통과.

운영에서 바로 할 수 있는 조치:
1. 2026-09-23, 25, 26 등 지난 날짜의 알림을 비활성화하고 다시 조회한다.
2. SONGPA_HTTP_ENABLED=true와 최신 배포 버전을 확인한다.
3. 올림픽은 우선 감시 날짜와 시간대 수를 줄여 한 날짜 조회의 성공 여부를 확인한다. 운영 계정으로 별도 로컬 로그인을 병행하지 않는다.
4. 올림픽 원문 로그에서 'provider 전체 조회 timeout after 240.0초'인지 페이지 이동·로그인·선택 단계의 개별 timeout인지 구분한다. 코드에는 각 회차 후 networkidle을 최대 10초 기다리는 경로가 있어 회차 수에 따라 대기가 누적될 수 있다. 이번 올림픽 타임아웃의 직접 원인은 운영 원문 로그 확보 전까지 미확정이다. 제한시간만 늘리면 중복 대기와 느린 조회를 가릴 수 있으므로 우선 실패 단계를 확인한다.

후속 변경은 지난 조건 자동 비활성화와 함께 커밋·푸시한다. 운영 배포의 성공 여부는 별도 확인이 필요하다.


## 지난 조건 자동 비활성화

한국 날짜 기준으로 예약일이 오늘보다 이전이면 모든 사용자의 조건을 enabled=false로 저장한다. 계정이 비활성 상태이거나 텔레그램이 연결되지 않은 사용자도 동일하게 정리한다. 조건과 기존 조회 기록은 삭제하지 않는다. 오늘과 미래 조건, 이미 수동으로 비활성화한 조건은 유지한다.

상태 조회 시 자동 비활성화를 직렬 저장 큐에서 처리하고, 상태 저장 시에도 검사해 지난 조건을 다시 켜는 요청으로 재활성화되지 않게 한다. 자동 비활성화 사유 DATE_PASSED와 처리 시각을 기록한다. 저장된 조건이 없는 계정에도 같은 규칙을 적용한다.

검증: 전체 작업 폴더 30개 파일 / 290개 테스트 통과. KST 자정 경계, 여러 사용자, 저장된 enabled 값, 과거 조건 재활성화 방지, 동시 저장 시 새 조건 보존을 확인했다.

커밋 대상만 추출한 검증: 27개 파일 / 258개 테스트 통과.
