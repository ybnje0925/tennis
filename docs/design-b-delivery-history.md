# B안 UI와 사용자 발송 이력

검토 브랜치: `codex/design-b-delivery-history`. 운영 배포는 수행하지 않았습니다.

## 화면

첨부 `tennis-ui-concepts (1).html`의 B안 앱 내부 스타일을 사용하고 기존 Express + vanilla JS 구조를 유지합니다. 모바일 메뉴는 내 알림 / 조회 결과 / 새 알림 / 조회 현황 / 설정이며 PC는 사이드 메뉴를 사용합니다. 정상 로그인·새로고침 시 내 알림이 기본입니다. 새 알림은 시설 선택 → 날짜·시간 선택의 2단계입니다. 초대, 기기 연결, 텔레그램 연결, 시설 선택 제한, 노원 코트·이용시간, 면목 계절 회차, 시간대 상관없음, 상태별 정렬·필터, 정지/재개/삭제, 서울시 탐색, 조회 로그 및 관리자 API를 보존했습니다.

시설 목록은 `/api/options`를 사용합니다. 시안과 달리 최신 코드의 노원 시설도 표시합니다. 면목 잔여 현황 카드는 제거했으며 빈자리 수집·조건·발송은 유지합니다. 목업 헤더, 프레임, 강제 상태 도구, 예시 데이터·토스트는 앱에 포함하지 않습니다. 빈 목록에서도 오늘 발송 이력으로 이동할 수 있습니다.

## 기록과 집계

- 기존 직렬화/원자적 rename 저장을 사용하는 `state.json`에 `deliveries`와 `deliveryStartedAt`을 추가합니다. 다른 저장 서비스나 마이그레이션 명령은 없습니다.
- 발송 전 `pending` 저널을 먼저 저장합니다. 저장 실패 시 API를 호출하지 않습니다. 응답이 HTTP 성공이고 JSON `ok:true`인 뒤 `sent`, 메시지 ID, 발송 시각 및 기존 중복 방지 정보를 함께 저장합니다. Telegram 응답에 `date`가 있으면 그 시각을 사용합니다.
- 메시지 1개 성공 = 1건입니다. 한 digest의 슬롯 수와 구분합니다. 실패는 성공에서 제외합니다. 현재 빈자리나 수신·읽음 확인을 의미하지 않습니다. 집계와 날짜 그룹은 Asia/Seoul입니다.
- 명확한 전송 실패는 `failed`로 저장합니다. 다음 기존 조회 주기에서 같은 watch/슬롯 묶음 재시도는 같은 ID와 attempts에 연결되며, 성공하면 해당 행이 성공으로 바뀝니다. 새로 열린 빈자리에 실제로 새 메시지를 보내면 새 ID를 기록합니다.
- 응답 유실·해석 불가 또는 발송 성공 후 저장 실패는 실제 결과를 확정할 수 없습니다. `pending`을 유지하여 같은 슬롯의 자동 재발송을 막고 집계 제외 건수를 화면에 알립니다. 재시작 뒤에도 유지됩니다. Telegram에는 임의의 idempotency key나 송신 이력 재조회 API가 없으므로 결과를 추정하지 않습니다. 이 상태의 자동 해제나 강제 재발송 UI는 추가하지 않았습니다. 운영자는 해당 ID와 로그를 확인해야 합니다.
- 따라서 기존 송신 함수의 네트워크 오류에 대한 즉시 3회 반복은 제거했습니다. 응답 유실 후 중복 메시지를 보내는 것을 막기 위한 변경이며, 시설 조회 주기·운영시간·야간 중지는 변경하지 않았습니다.
- 기존 `telegram_sent` 중 `userId`가 정확한 이벤트는 상세 없는 성공 기록으로 재사용합니다. `deliveryId`가 있는 신규 이벤트는 이중 집계하지 않습니다. 시설은 기록된 venue ID만 이름으로 표시하며 이용 날짜·시간·내용은 추정하지 않습니다. 식별자가 없는 기록과 재시도 연결이 불가능한 과거 실패는 사용자 이력에 넣지 않습니다.
- 기존 analytics 이벤트에는 자동 삭제/보관 기간 제한이 없습니다. 신규 이력도 같은 저장 수명을 사용합니다. 누적은 **현재 보관된 식별 가능한 기록의 성공 수**이고 기록 시작/상세 시작을 명시합니다. 연결 확인용 메시지와 봇 첫 연결 응답은 기존 빈자리 이벤트 집계와 마찬가지로 제외합니다.

## API와 보존

`GET /api/deliveries?period=all|today&status=all|sent|failed&offset=0`은 인증된 세션의 사용자만 조회합니다. userId 쿼리는 사용하지 않습니다. 20개씩 반환하고 `nextOffset`으로 더 보기 합니다. 최근 10개 시도 정보와 총 시도 수만 응답합니다. `summary=1`은 메시지 목록 없이 집계만 반환하며 백그라운드 30초 갱신에 사용하여 펼친 메시지·페이지 상태를 유지합니다. chat ID, 토큰, 내부 오류, 내부 키, Telegram 메시지 ID는 응답에서 제외하고 오류는 일반 문구로 응답합니다. `Cache-Control: no-store`를 적용합니다.

저장 경로는 기존 `DATA_DIR`, 또는 Railway의 `RAILWAY_VOLUME_MOUNT_PATH/data`, 또는 로컬 `data`입니다. 기존 영속 Volume 마운트/경로를 그대로 사용해야 합니다. Volume 없는 임시 파일 시스템은 배포·재생성 시 보존되지 않습니다. 외부 서비스를 추가하지 않습니다. 단일 프로세스의 기존 JSON 저장 모델이며 다중 인스턴스 간 동시 쓰기는 이번 범위에서 추가하지 않았습니다. 장기 보관 데이터는 서버에서 읽고 집계하지만 전체 이력을 브라우저에 보내지는 않습니다.

## 검증

- `npm test`: 36개 파일, 342개 테스트 통과. 기존 시설·스케줄·인증·관리자·중복 방지 테스트 포함.
- 신규: digest 메시지 집계, 실패→성공 연결, KST 자정 경계, 안전한 과거 이벤트, 페이지네이션, 사용자 A/B 격리, 401/no-store/정보 제외, 모듈·서버 재시작, HTTP 200 + ok:false, 성공 뒤 저장 실패 및 불확실 결과의 재전송 방지, 발송 전 저장 실패.
- `node scripts/verify-design-b.mjs`: 실제 Chromium에서 첨부 시안 화면과 전환 확인. 앱 360/390/430px 및 PC 1440px, 하단 메뉴 순서·가로 넘침·제출 버튼 여백, 필터, 실제 로컬 API 등록/정지/재개/삭제, 긴 시설명·내용/HTML escape, 불러오는 중/실패/빈 목록, 연결 전후·기존 계정 연결 화면을 확인했습니다.
- 브라우저 검증은 임시 디렉터리·가짜 계정·빈 Telegram 토큰으로 실행하며 스케줄러를 시작하지 않습니다. 서울시 외부 카탈로그 응답과 이력 장애 상태만 브라우저에서 주입합니다. 발송 이력/등록/정지/삭제 API는 실제 로컬 서버를 사용합니다.
- 캡처: `artifacts/design-b/`. `home-390.png`, `results-390.png`, `new-390.png`, `home-1440.png`, `results-1440.png`, `empty-390.png`, `disconnected-390.png`, `entry-390.png` 등.
- 실제 Telegram 수신, 운영 Railway Volume 재시작, 실기기 키보드·safe area는 운영 환경에서 확인하지 않았습니다. 키보드 대응은 visualViewport 기반으로 구현했습니다. 외부 구장의 실시간 조회 회귀는 기존 mock/fixture 테스트 범위입니다.
